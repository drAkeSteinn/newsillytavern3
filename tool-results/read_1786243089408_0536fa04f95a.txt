   475→**File:** `src/lib/lorebook/attribute-resolver.ts` — `resolveLorebookAttributeKeys(lorebooks, context)` (line 81)

   487→- **Static mode** (lines 300-306): if `evaluateCondition(attrValue, staticCondition.operator, staticCondition.value)` returns true → return `entry.content` formatted with `<START>` dialogue processing. Else return `null`.

   501→### `evaluateCondition` — operator evaluation
   502→**File:** `src/lib/lorebook/attribute-resolver.ts` lines 423-467
   503→
   504→```ts
   505→function evaluateCondition(attrValue, operator: AttributeComparator, compareValue): boolean {
   506→  // String operators (always case-insensitive)
   507→  if (operator === 'contains') return String(attrValue).toLowerCase().includes(String(compareValue).toLowerCase());
   508→  if (operator === 'not_contains') return !String(attrValue).toLowerCase().includes(String(compareValue).toLowerCase());
   509→
   510→  // Try numeric comparison first
   511→  const numAttr = typeof attrValue === 'number' ? attrValue : parseFloat(String(attrValue));
   512→  const numComp = typeof compareValue === 'number' ? compareValue : parseFloat(String(compareValue));
   513→  const bothNumeric = !isNaN(numAttr) && !isNaN(numComp);
   514→
   515→  if (bothNumeric) {
   516→    switch (operator) {
   517→      case '<':  return numAttr <  numComp;
   518→      case '<=': return numAttr <= numComp;
   519→      case '>':  return numAttr >  numComp;
   520→      case '>=': return numAttr >= numComp;
   521→      case '==': return numAttr === numComp;
   522→      case '!=': return numAttr !== numComp;
   523→      default: return false;
   524→    }
   525→  }
   526→
   527→  // Text comparison (one or both values are non-numeric)
   528→  const strAttr  = String(attrValue).toLowerCase();
   529→  const strComp  = String(compareValue).toLowerCase();
   530→  switch (operator) {
   531→    case '==': return strAttr === strComp;
   532→    case '!=': return strAttr !== strComp;
   533→    case '<': case '<=': case '>': case '>=': return false;  // numeric-only
   534→    default: return false;
   535→  }
   536→}
   537→```

   658→## 5. Existing Patterns to Reuse
   659→
   660→1. **Attribute operator evaluation** — `evaluateCondition(attrValue, operator, compareValue)` in `src/lib/lorebook/attribute-resolver.ts` lines 423-467. Handles 8 operators (`==`, `!=`, `<`, `<=`, `>`, `>=`, `contains`, `not_contains`), numeric-vs-string auto-detection, case-insensitive string comparison. Should be extracted to a shared utility (e.g., `src/lib/attributes/evaluate.ts`) so the proactive hook/route can import it without coupling to the lorebook module.
   661→
   662→2. **Priority resolution** — `resolveSingleAttributeEntry` in `src/lib/lorebook/attribute-resolver.ts` lines 278-341, specifically lines 316-329. Sorts matching conditions by `priority` descending and either takes the top match (`first-match`) or joins all with `\n\n` (`concat-all`). This is exactly the pattern needed for proactive case selection.
   663→
   664→3. **Rotation / random-without-recent-repeat** — `/api/chat/proactive/route.ts` lines 1014-1026. Finds unused indices by filtering out `clientUsedNudgeIndices`, picks random unused; if all used, picks random from full pool. Client tracks state in `usedNudgeIndicesRef` (`use-proactive-messages.tsx` line 101) and sends it in the request body (line 359). This pattern can be directly applied to proactive cases for `linear`/`random` modes.
   665→
   666→4. **{{key}} substitution (case-insensitive + re-resolve)** — `resolveLorebookAttributeKeys` (`key-resolver.ts` lines 620-667) and `resolveLorebookEntryKeys` (lines 686-733). Both:
   667→   - Sort keys by length descending to prevent partial replacement.
   668→   - Use case-insensitive regex `\{\{escapedKey\}\}` with `gi` flag.
   669→   - After replacement, **re-run** `resolveTemplateVariables` and `resolveStatsKeys` on the result, because injected content may itself contain `{{char}}`, `{{vida}}`, etc. This recursive resolution is critical for layered templates.
   670→
   671→5. **`buildKeyResolutionContext` factory** — `src/lib/key-resolver.ts` lines 1027-1063. Already accepts every piece of data needed: `lorebookAttributeKeys`, `lorebookEntryKeys`, `outletSections`, `inventoryData`, `resolvedStats`, `personaResolvedStats`, `questTemplates`, etc. The proactive route already builds this (lines 568-583) and passes it to every `resolveAllKeys` call.
   672→
   673→6. **`resolveAllKeys` main entry** — `src/lib/key-resolver.ts` lines 945-984. Single function that runs all 7 resolution phases. Always use this (never call individual phase functions directly) to ensure consistent resolution order.
   674→
   675→7. **SSE streaming pattern** — The proactive route returns a `ReadableStream` (line 1119) and uses `controller.enqueue(createSSEJSON({...}))` to emit typed events. Client-side reader parses `data: {...}` lines split by `\n\n`. This is the established pattern for any new event types (e.g., a `case_selected` event before `proactive_start` if the redesign needs to communicate which case won).
   676→
   677→8. **ProactiveMessageInfo metadata** — `src/types/index.ts` lines 1340-1349. Already has `nudgeIndex` and `topic` fields. Add `caseIndex?: number` (or `caseId?: string`) for the redesign's case tracking.
